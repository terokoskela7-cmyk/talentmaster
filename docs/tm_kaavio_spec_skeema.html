Spec-skeema & putki

v2 · lukitut opit: pilotit (h0 · j_p6) + y_h-perhe 10/10 + editori

Tämä on kaavioiden tekninen sopimus: koordinaatisto, notaatiokatalogi, spec-JSON-skeema, arkkityyppimalli, Gemini-erägeneroinnin kehote ja validaattorin portit. Kaikki pilotissa todennetut säännöt on lukittu tänne. Renderöijä + validaattori toteutetaan tätä vasten.

§1

Koordinaatisto

Opta 100×100, origo ylävasen. x = kentän leveys (0–100), y = kentän pituus (0–100). Sama järjestelmä kuin Opta/Stats Perform → siirrettävä ja valmis dataintegraatioon.

Hyökkäyssuunta per konsepti kentässä suunta (oletus ylos = vastustajan maali y≈0). Renderöijä kääntää tarvittaessa.

Mittasuhde-sääntö (pakollinen): Opta-yksiköt eivät ole metreissä yhtä suuret — x-yksikkö 0,68 m, y-yksikkö 1,05 m. Renderöi sama px/metri molemmilla akseleilla: skaala_y = skaala_x × 1,544. Muuten kenttä vääristyy.

Laajennus — pelaajakohtainen näkökenttä, peliasento ja katve

Miksi: spec.cone oli GLOBAALI ja sidottu siihen yhteen pelaajaan jonka rooli sattui olemaan vastaanottaja. Kartio ei kuitenkaan ole rooli vaan havainto, eikä muiden pelaajien peliasentoa voinut kääntää lainkaan (se laskettiin aina palloa kohti). Näkökenttä on siksi siirretty pelaajan ominaisuudeksi.

pelaaja: {
  ...ennallaan...,
  "suunta": -58,            // UUSI. Kehon/katseen suunta asteina. Editoitava.
                            //   Lukujärjestys: suunta → avoin (legacy) → osoita palloon (oletus).
  "nakokentta": {           // UUSI. TÄMÄN pelaajan näkökenttä. Valinnainen, mille tahansa pelaajalle.
    "half": 58,             //   puolikulma asteina, 0 < half ≤ 180  (leveys)
    "r": 42,                //   syvyys metreinä, r > 0              (sama yksikkö kuin vanha cone.r)
    "katve": true           //   valinnainen: piirrä peittoalue suunnan taakse (mitä pelaaja EI näe)
  }
}

spec.cone  →  DEPREKOITU. Ei virhe, mutta migroidaan kirjoitushetkellä:
             kaavioNormalisoiNakokentta(spec) siirtää sen vastaanottajan nakokentta-kentäksi
             ja perii suunnan avoin-arvosta. Idempotentti. Renderöijä sietää molempia muotoja,
             joten migroimaton dokumentti näyttää ennallaan.

Yhteensopivuus: suunta ja nakokentta ovat VALINNAISIA → jokainen aiemmin validi spec pysyy validina. Vanha {cone, avoin}-dokumentti renderöityy tavulleen identtisesti migraation jälkeen (todennettu SVG-vertailulla).

Yksi totuus: validaattori lib/tm_kaavio_validate.js valvoo nämä rajat; renderöijä lib/tm_kaavio_render.js toteuttaa facing(p)-säännön; migraatio ja setterit ovat lib/tm_kaavio_editori.js:ssä. Katve on geometriaa, ei tekstiä (§32) — renderiin ei lisätä käännettäviä merkkijonoja, selitteet tulevat vain Selite-työkalusta.

Renderöijän robustisuussäännöt (contact-sheet-proofissa lukitut): (1) näkökentän säde cone.r ilmaistaan metreissä, ei pikseleinä → siirrettävä katselukoon yli. (2) Selite pidetään aina kentän sisällä: renderöijä ankkuroi tekstin automaattisesti reunan mukaan (x>58 → oikea-ankkurointi), koska generaattori sijoittaa selitteet vapaasti.

§3

Spec-JSON (per konsepti)

{
  "avain": "t_h0",              // curriculum-avain (enum, ei käänny)
  "suunta": "ylos",             // hyökkäyssuunta
  "pelimuoto": "8v8",           // → pelaajamäärän raja (validoidaan)
  "nakyma": "puolustuskolmannes", // kentän rajaus: kolmannes | puolisko | koko
  "pelaajat": [                        // rooli ∈ vastaanottaja|syöttäjä|vaihtoehto|paine|tuki
    { "id":"T", "joukkue":"oma", "rooli":"vastaanottaja",
      "x":43, "y":74, "gk":false, "pallo":false,
      "suunta":-58,               // katsesuunta (astetta) — editoitava; "avoin" on vanha nimi (siedetään)
      "nakokentta": { "half":58, "r":42, "katve":true },  // PELAAJAKOHTAINEN (ks. laajennus yllä)
      "korostus":true },
    { "id":"V1","joukkue":"vastustaja","rooli":"paine","x":40,"y":63 },
    { "id":"P", "joukkue":"oma","rooli":"syöttäjä","x":50,"y":88,"pallo":true },
    { "id":"LP","joukkue":"oma","rooli":"tuki","x":18,"y":70 },
    { "id":"A", "joukkue":"oma","rooli":"vaihtoehto","x":56,"y":30 }
  ],
  "liikkeet": [                        // tyyppi: juoksu|syotto|kuljetus|laukaus
    { "id":"m1","tyyppi":"syotto", "from":{"ref":"P"},  "to":{"ref":"T"} },
    { "id":"m2","tyyppi":"juoksu", "from":{"ref":"LP"}, "to":{"x":22,"y":50} },
    { "id":"m3","tyyppi":"laukaus","from":{"ref":"A"},  "to":{"x":50,"y":1} }
  ],                                       // from/to = {ref:id} (seuraa pelaajaa) TAI {x,y} (vapaa piste)
  // LUOKKA C — kaikki kolme VALINNAISIA; §6-validaattorin portit alla.
  "vyohyke":      { "x":29,"y":64,"w":40,"h":22 },      // YKSI objekti per kaavio (ei taulukko)
  "korkeuslinjat": [ { "id":"kl1", "y":58 } ],
  "peittovarjot":  [ { "id":"pv1", "from":"V1", "to":"A" } ],  // from/to = pelaajan id
  "selitteet": [                       // TAULUKKO; t = kielikartta, ≥1 kieli riittää
    { "id":"s1", "x":24, "y":18,
      "t": { "fi":"Avaa kylkiasentoon", "sv":"Öppna kroppen", "en":"Open your body" } }
  ]
}

Selitteet ovat INLINE-TEKSTIÄ, eivät curriculum-avaimia. selitteet on taulukko [{id, x, y, t}], jossa t on kielikartta. Validaattori vaatii vähintään yhden kielen — ei kaikkia kolmea. Syy on kahden eri sisältölajin ero: kanoninen kirjasto on kuratoitua master-sisältöä ja täyttää kaikki kolme (§32-trilingua), kun taas valmentajan oma selite on vapaatekstiä hänen omalla kielellään — sitä ei käännetä eikä pidä pakottaa kääntämään (aiempi kolmen kielen pakko esti tallennuksen kokonaan). Renderöijä tekee kielifallbackin t[lang] || t.fi || t.sv || t.en.

Historiallinen huomio: prototyypissä selitteet olivat avainviittauksia curriculumiin ({"otsikko":"t_h0.nimi"}). Se muoto EI ole tuotannossa — validaattori ei osaa käsitellä sitä lainkaan (se odottaa taulukkoa). Älä palauta sitä.

Luokka C — peittovarjo · korkeuslinja · vyöhyke (§6-portit)

Nämä piirtyivät renderöijässä ennen kuin ne olivat skeemassa, joten validaattori ei valvonut niitä: kentän ulkopuolinen vyöhyke ja olemattomaan pelaajaan osoittava peittovarjo menivät molemmat läpi puhtaana. Siksi työkalut oli jätetty pois. Nyt portit ovat olemassa ja muoto on lukittu renderöijää vasten — sitä ei saa muuttaa neuvottelematta.

  • vyohyke — x,y,w,h 0..100; w>0, h>0; x+w ≤ 100, y+h ≤ 100. Yksi per kaavio.
  • korkeuslinjat[] — y 0..100; id uniikki. Linja on aina kentän levyinen (renderöijä piirtää x 2..98).
  • peittovarjot[] — from/to viittaavat olemassa oleviin pelaajiin (viite-eheys); from ≠ to; id uniikki. Pelaajan poisto kaskadipoistaa häneen viittaavat varjot.

Sopimuksen kuluttajat pysyvät synkassa: §3-skeema on sopimus, ja sen toteuttavat sama koodi neljässä paikassa — renderöijä, editori (valmentajan raahaus/lisäys-työkalut), §6-validaattori ja generointikehote. Uusi notaatio lisätään kaikkiin neljään yhtä aikaa (esim. laukaus + gk lisättiin y_h9:n paljastettua puutteen).

§4

Arkkityypit & parametrointi

79 fundamenttia = ~13 faasi-arkkityyppiä × pelipaikka. Arkkityyppi on pohjaspec; pelipaikka parametroi kaista×kolmannes-akselilla (5 kaistaa: laita·puolitila·keskus·puolitila·laita × 3 kolmannesta).

  • Pohja määrittää rakenteen (vastaanottaja + referenssit + liikkeet + notaatio).
  • Positio-override siirtää vyöhykkeen ja referenssipisteet oikeaan kaistaan/kolmannekseen; pelimuoto/ika antavat pelaajamäärän datasta.
  • youth (14) + joukkue (16) = yksilöllisempiä (koko kenttä); tehdään tapauskohtaisesti.
§5

Gemini-erägeneroinnin kehote

Sama eräputki kuin käännöksissä (positio/prefix kerrallaan). Liitä kehotteeseen konseptin teksti + arkkityyppipohja.

Tuota VAIN validi JSON annetun skeeman mukaan (§3). Säännöt:
- Koordinaatit Opta 100x100 (x leveys, y pituus), origo ylävasen, hyökkäys "suunta".
- Pelaajamäärä EI ylitä pelimuotoa. Jokainen liike/syötto viittaa olemassa olevaan
  pelaajan id:hen (tai on pallosyötto ilman pelaajaa). Keskityksellä on kohde.
- Notaatiotyypit VAIN: juoksu | syotto | kuljetus | laukaus. Merkkerit skeeman roolit.
- Liikkeen from/to = {ref:pelaajan-id} (seuraa pelaajaa) TAI {x,y} (vapaa piste). Maalivahti: pelaaja "gk":true.
- "avoin" = pelaajan auki-suunta asteina; kylkiasento niin että hän näkee pallollisen
  JA lähimman vastustajan. ÄLÄ laita pelaajaa selka palloon.
- Selitteet ovat curriculum-AVAIMIA (esim. "t_h0.nimi"), ei tekstiä.
- Palauta pelkkä JSON, ei selityksiä.
Konsepti: <liitä nimi · pelitilanne · KPI:t · pelimuoto · pelipaikka>
Arkkityyppipohja: <liitä pohjaspec>
§6

Validaattori — portit ENNEN renderiä

Deterministinen validaattori (sama kuri kuin käännöksen häviöttömyysportti):
  • Skeema: pakolliset kentät, tyypit, sallitut enumit (notaatiotyyppi, joukkue, rooli).
  • Rajat: kaikki koordinaatit 0–100.
  • Pelaajamäärä = pelimuoto (ei enempää per joukkue).
  • Viite-eheys: jokainen liike.from/to jossa ref viittaa olemassa olevaan pelaaja-id:hen; vapaa piste {x,y} rajoissa. Sama peittovarjo.from/to. Näkökenttä EI ole viite: se asuu pelaajaobjektin sisällä (pelaajat[].nakokentta), joten sillä ei ole erillistä pelaaja-viitettä joka voisi jäädä orvoksi.
  • Notaatio-enum: tyyppi ∈ {juoksu, syotto, kuljetus, laukaus}; ≤1 pallollinen. PÄIVITETTY: cone-kytkös vastaanottajaan on purettu — näkökenttä on nyt pelaajakohtainen nakokentta (ks. laajennus alla).
  • Selite-resolvi: jokainen selite_avain löytyy curriculumista (fi/sv/en).
  • Enum-invariantti: avain ei käänny.
Punainen validaattori = spec ei mene renderiin. Sen jälkeen contact sheet (valmennuspäällikkö silmäilee kaikki pikkukuvaruudukossa, merkkaa taktisesti väärät).

Tulevaisuus auki (arkkitehtuurivalinta)

  • Animaatio: liike.polku riittää SMIL/CSS-animointiin — ei nyt, ei suljettu pois.
  • Analytiikka/tracking: Opta-koordinaatit = yhteensopiva oikean ottelu­datan kanssa.
  • Havaintoelementit & tasot: h0-perhe voi renderöityä 4 havaintoelementtinä (välit·lähin vastustaja·vapaat omat·vapaa tila) ja tasoilla 1–3 (asteikko).
  • Siirrettävyys: kieli-neutraali spec + standardikoordinaatit → VP, Master, Pelaaja, export.
